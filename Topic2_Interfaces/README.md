# Topic2 — Интерфейсы и инверсия зависимостей (Теория и практические примеры)

Цель: дать понятное лекционное объяснение, как и зачем использовать интерфейсы, абстракции и внедрение зависимостей в коде автотестов и утилит.

Ключевые понятия
- `interface` — контракт: набор сигнатур методов и свойств без реализации. Интерфейс описывает «что должно быть сделано», но не «как». 
- Инверсия зависимостей (Dependency Inversion Principle) — из SOLID: высокоуровневые модули не должны зависеть от низкоуровневых; оба должны зависеть от абстракций.
- Внедрение зависимостей (Dependency Injection) — способ передачи зависимостей (через конструктор, сеттер или метод). Это делает код более гибким и подменяемым.

Лекционный материал
1. Почему интерфейс лучше прямой зависимости от класса
- Соединяя код с интерфейсом, вы декларируете контракт и убираете жесткую привязку к реализации. Тест/сервис может работать с любой реализацией этого интерфейса.
- Пример: `ILoginService` может иметь реализации `UiLoginService`, `ApiLoginService`, `FakeLoginService`.

2. Способы внедрения зависимостей
- Конструктор (рекомендуется для обязательных зависимостей):
  - `public LoginTest(ILoginService service) { _loginService = service; }`
- Свойство (для опциональных зависимостей).
- Метод (для локальной подмены в отдельных сценариях).

3. Жизненные циклы (в DI-контейнерах)
- `Transient` — новый экземпляр каждый раз.
- `Scoped` — один экземпляр на сессию/запрос (в Web/тестовой среде — по контексту).
- `Singleton` — один экземпляр на приложение.

4. Примеры кода (консольная модель)
- Интерфейс:
  - `public interface ILoginService { void Login(string user, string pass); bool IsLoggedIn { get; } }`
- Реализации:
  - `UiLoginService` — вызывает симуляцию кликов/ввода.
  - `ApiLoginService` — делает HTTP-запросы (в учебном примере имитируем ответ).
  - `FakeLoginService` — простой фейк, который сразу переводит в состояние `IsLoggedIn = true`.
- Внедрение через конструктор и использование в `LoginTest` показывает, что один и тот же тестовый код работает с разными реализациями.

5. Общие ошибки и анти-паттерны
- Инжектировать конкретные реализации вместо интерфейсов — уменьшает гибкость.
- Использовать глобальные статические singletons для зависимостей — усложняет изоляцию примеров.
- Держать в интерфейсе слишком много методов (тогда это станет «божественным» интерфейсом) — лучше разбивать на маленькие контрактные интерфейсы.

Практика (консольные задания)
- Реализовать `FakeLoginService` и показать работу `LoginTest` с ним.
- Показать регистрацию зависимостей в `ServiceCollection` (пример в `Program.cs`) и получить сервис через `ServiceProvider`.
- Написать простую реализацию, где `ApiLoginService` возвращает разные коды ответов и проверить, как `LoginTest` их обрабатывает.
